## 一、为什么需要这份文档

项目里最容易出现、也最贵的错误，是**以为链路是通的**。

组会上说"我这边没问题"，实际是"我没测过"；联调时车不动，五个组互相看，谁都觉得不怪自己。根本原因是**没有人把完整链路画出来**——每个组只看自己那一段，中间那些"没人负责的缝"就没人管。

本文档的目标就是**把链路显式地拆开**，让每一段都有明确的主人。

**三条使用原则**：

1. 任何一段链路出问题，**先按本文档定位到段，再找该段的负责人**——不要跨段猜
2. 本文档只描述**数据怎么流**，接口的具体格式看《通信协定》
3. 本文档中标 ⚠️ 的条目，是**当前没有明确负责人或存在风险**的地方

## 二、全局链路总览

### 2.1 三条独立通路

车上其实有**三条互不相干**的通路，混在一起讲是理解困难的主因。先分开看：

| 通路 | 路径 | 是否经过 Jetson | 是否经过 ROS | 延迟 | 用途 |
|---|---|---|---|---|---|
| **A · 车内串口链路** | Jetson ↔ STM32 扩展板 | 起点 | 是 | ~10 ms | 车身数据的进出总口 |
| **B · 无线遥测链路** | 监控端 ↔ LoRa ↔ Jetson | 是 | 是 | 数十~数百 ms | 150m 外的远程监控与轻量指令 |
| **C · 人工接管链路** | 遥控器 ↔ SBUS 接收机 ↔ STM32 | **否** | **否** | ~14 ms | 最后一道人工保险 |

**关键认知**：通路 C **完全绕过 Jetson 和 Linux**。哪怕 Jetson 死机、ROS 崩溃、LoRa 掉线，遥控器依然能直接控制车轮。这是设计上的**故意冗余**，不是巧合——不要试图把遥控器也接入 ROS，那等于把保险丝接到主电路上。

### 2.3 五级抽象（理解"指令"的关键）

"让车前进 150 米"这句话在链路里其实被**逐级翻译了五次**，每次换一种语言、换一个负责人：

| 级别 | 表达形式 | 典型频率 | 负责组 | 举例 |
|---|---|---|---|---|
| **① 任务级** | 自然语言 / 任务编号 | 一次 | 通信组（翻译） | "前进 150 米" |
| **② 目标级** | 目标点坐标 `(x, y, yaw)` | 一次 | 算法组 | "去 (150, 0)" |
| **③ 路径级** | 一串路径点 / 速度曲线 | 1~10 Hz | 算法组（Nav2） | 沿车道直行 |
| **④ 速度级** | `Twist`：vx, vy, ωz | **20~50 Hz** | 控制组 | `vx=0.3` m/s |
| **⑤ 电机级** | 4 路 PWM 占空比 | 1 kHz | STM32 固件 | 电机 A 占空比 42% |

> ⚠️ **最常见的误解**：以为"发一条指令"就完了。实际上从 ① 到 ⑤ 要经过 **5 次转换、4 个节点**，任何一环没实现，车就不动。**"我发了指令车不动"从来不是通信组一家的事**——必须逐级排查（见第五章）。

## 三、逐段链路详解

以下按数据**流入车**（下行）与**流出车**（上行）两个方向拆解，每一段都标出：传输内容、承载形式、负责人、断了的症状。

### 3.1 下行链路：指令怎么进车

#### 段 D1 · 监控端 → LoRa 发射（150m 外）

| 项 | 内容 |
|---|---|
| 传输内容 | 指令帧（帧头+序号+长度+命令字+数据+CRC16+帧尾） |
| 承载形式 | LoRa 433/470 MHz 无线 |
| 负责人 | 通信组 |
| 断了的症状 | 车端完全无反应，`/link_status` 显示链路中断 |
| 排查手段 | 见排查手册第 5.7 节（抓原始字节） |

指令类型仅限**轻量级**（急停 / 召回 / 模式切换）——注意，**不承担正常行驶控制**：

> ⚠️ **重要设计约束**：150m 部署场景下，车必须**自主导航**（车长仅 220mm，150m 外不可见；按 0.7 m/s 走完需约 3.5 分钟，人工全程遥控不现实且误操作风险高）。LoRa 因此**只用于异常干预与状态监控**，不用于驾驶。这是本项目遥测链路的设计前提。

#### 段 D2 · 车端 LoRa → bridge 节点（串口）

| 项 | 内容 |
|---|---|
| 传输内容 | 原始字节流（LoRa 模块只是"无线串口线"，**不认 ROS、不认话题**） |
| 承载形式 | USB 串口 `/dev/lora` |
| 负责人 | **通信组（核心产出）** |
| 断了的症状 | LoRa 指示灯闪但 ROS 里无任何话题 |
| 排查手段 | `sudo cat /dev/lora \| xxd`；`sudo fuser -v /dev/lora` |

**这是通信组最关键的一段**。LoRa 模块本身是**透传**的（配置一次参数后，串口进什么、空中就发什么），所以车端**必须有一个自写的节点**做翻译：

```
bridge 节点职责（双向）：
  下行：读串口 → 校验 CRC → 解析帧 → 发布 ROS2 话题
  上行：订阅 ROS2 话题 → 打包成帧 → 算 CRC → 写串口
```

> ⚠️ **实现禁忌**：**禁止在 ROS 回调函数里做阻塞式串口写**。应使用「队列 + 定时器」模式（下行指令入队，定时器按 2~5 Hz 出队发送）。否则串口写超时会直接阻塞 ROS 的执行器，整个节点的其他回调全部卡死——表现为"平时正常，一发指令就整体卡住"，极难定位。

#### 段 D3 · bridge → 车内 ROS 话题

| 项 | 内容 |
|---|---|
| 传输内容 | 语义指令（如 `急停` / `召回` / `目标点`） |
| 承载形式 | ROS2 话题（DDS 传输） |
| 负责人 | 通信组（**定义**），算法组/控制组（**订阅并响应**） |
| 断了的症状 | 话题有数据，但车不响应 |

**这里有两个设计选择，必须与控制组约定**：

| 方案 | 路径 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **语义指令**（推荐默认） | bridge → `/mission_cmd` → 算法组/控制组解析 → `/vel_raw` | 安全，经过状态校验 | 环节多，延迟略高 | 召回、模式切换、目标点 |
| **直发速度**（快路径） | bridge → `/vel_raw` → base_node | 最快 | **绕过所有安全校验** | **仅限急停** |

> ⚠️ **急停建议走快路径**，但必须同时满足：① 速度为零，绕过校验无风险；② 优先级最高，不能被自主算法覆盖。这个"优先级仲裁"由谁实现在《通信协定》第五章列为待确认项，**需与控制组拍板**。

#### 段 D4 · ROS 话题 → base_node

| 项 | 内容 |
|---|---|
| 传输内容 | `geometry_msgs/msg/Twist`：`linear.x/y`、`angular.z` |
| 承载形式 | ROS2 话题 `/vel_raw`，建议 **20 Hz** |
| 负责人 | 算法组（**发布**）、控制组（**接收**） |
| 断了的症状 | `ros2 topic info /vel_raw` 显示 `Subscription count: 0` |

`base_node` 是 **Yahboom 官方提供的底盘驱动节点**，它做两件事：

- **订阅** `/vel_raw` → 把 Twist 转成底盘的串口协议 → 写串口下发
- **读取**串口上行数据 → 解析 → **发布** `/odom_raw`

> ⚠️ **关键问题（需与控制组分工）**：`base_node` 是否沿用官方版本、还是需要修改？如果修改，谁维护？这是通信组与控制组的**任务重叠区**——建议分工为「**控制组管启动流程与节点维护，通信组管诊断方法与故障定位**」。

#### 段 D5 · base_node → STM32（串口）

| 项 | 内容 |
|---|---|
| 传输内容 | 底盘私有串口协议帧（`rosmaster_lib` 已封装） |
| 承载形式 | 串口 `/dev/rosmaster`，波特率 **待实测确认** |
| 负责人 | 控制组 |
| 断了的症状 | 里程计不动 / 车轮不动，但 ROS 层全部正常 |
| 排查手段 | 排查手册第 5 章（抓字节、查占用、查波特率） |

**这一段是本项目最"黑盒"的一段**——协议由 STM32 固件定义，`rosmaster_lib` 只是客户端封装。如果怀疑这一段，用 `sudo cat /dev/rosmaster | xxd` 直接看字节流是最有效的判定手段。

#### 段 D6 · STM32 → 电机（固件内部）

| 项 | 内容 |
|---|---|
| 传输内容 | 4 路 PWM 占空比 |
| 承载形式 | STM32 内部（FreeRTOS 任务） |
| 负责人 | 控制组 |
| 断了的症状 | 串口有正确数据，但轮子不转 |

这里执行 **PID 闭环**：目标速度（来自串口）vs 实际速度（来自编码器）→ 修正 PWM。**慢速底盘（0.7 m/s 上限）对通信延迟不敏感**，这是本项目的一个有利条件。

#### 段 D7 · STM32 ← SBUS 遥控器（通路 C 汇合点）

| 项 | 内容 |
|---|---|
| 传输内容 | SBUS 串行信号（航模遥控器标准协议） |
| 承载形式 | 3 线信号线，直插 STM32，**不经过 Jetson** |
| 负责人 | 控制组（硬件接入） |
| 价值 | **Jetson 死机仍可用**，是最后一道人工保险 |

### 3.2 上行链路：数据怎么出车

上行链路是**遥测**，对安全不是硬需求——**断了只是"看不见"，不影响车继续走**。这一点要在设计时想清楚，避免为遥测可靠性过度投入。

#### 段 U1 · STM32 → base_node（串口）

| 项 | 内容 |
|---|---|
| 传输内容 | 编码器计数、电压、状态字 |
| 承载形式 | 串口 `/dev/rosmaster` |
| 负责人 | 控制组 |

#### 段 U2 · base_node → `/odom_raw`

| 项 | 内容 |
|---|---|
| 传输内容 | `nav_msgs/msg/Odometry`：位置、姿态、速度 |
| 承载形式 | ROS2 话题，建议 **30 Hz** |
| 负责人 | 控制组（**发布**），定位组（**消费**） |
| 注意 | ⚠️ **单位与坐标系必须与定位组对齐**（《通信协定》待确认项 5） |

**里程计原理**（理解这一段的关键）：车轮每转一圈 → 编码器产生固定个数的脉冲 → 乘轮径得位移 → 累加得位置。这就是**航迹推算（dead reckoning）**，优点是短时精确、缺点是会**累积误差**——所以必须有 GNSS 来修正（这就是定位组存在的理由）。

#### 段 U3 · 各组 → 通信组（遥测数据汇聚）

通信组需要向**四个组**订阅数据，才能拼出完整遥测帧：

| 来源组 | 需要的数据 | 用途 |
|---|---|---|
| 控制组 | `/odom_raw` | 速度、里程 |
| 定位组 | 融合后位置 `(x, y)` | 地图上的位置 |
| 算法组 | 任务状态（待机/行走/到达…） | 进度显示 |
| 各组 | 异常状态 | 告警 |

> ⚠️ **这里有个现实风险**：通信组的遥测节点**依赖四个组的输出**。如果某个组的话题名/类型迟迟不定，遥测就无法完成。**对策**：通信组应主动定义接口并通知各组（见《通信协定》三章），而不是等需求上门——**通信组是接口定义方，不是被动接需求方**。

#### 段 U4 · 通信组 → LoRa → 监控端

| 项 | 内容 |
|---|---|
| 传输内容 | 状态上报帧（电量、速度、里程、任务状态、经纬度），**2~5 Hz** |
| 承载形式 | LoRa 433/470 MHz |
| 负责人 | 通信组 |
| 编码要求 | 空中用**紧凑编码**（mm、0.001 rad/s 等），接收端解码后换算回 SI |

**为什么必须紧凑编码**：LoRa 带宽有限（SF10~SF12 下，实际速率可能只有几百到几千 bps），**每次传输都要精打细算**。这是《通信协定》4.4 节专门说明"传输编码"与"SIL 约定"区别的原因——两者不矛盾：**对外数据一律用 SI，但空中传输可以用紧凑编码**。

## 四、各组职责与接口边界

### 4.1 一张表看清"谁给谁什么"

| 发布方 | 接口 | 订阅方 | 状态 |
|---|---|---|---|
| **通信组** | `/mission_cmd` 远程指令 | 算法组 / 控制组 | 🔲 待定 |
| **通信组** | `/link_status` 链路状态 | （供监控与本地告警） | 🔲 待定 |
| **控制组** | `/odom_raw` 原始里程计 | 定位组 / 通信组 | 🔲 待定 |
| **控制组** | 底盘状态（电压等） | 通信组 | 🔲 待定 |
| **定位组** | 融合定位 `/odom` + TF | 算法组 / 通信组 | 🔲 待定 |
| **传感组** | `/scan` 激光雷达 | 算法组 | 🔲 待定 |
| **传感组** | 避障信息 | 算法组 / 通信组 | 🔲 待定 |
| **视觉组** | 识别结果（只传结论） | 算法组 / 通信组 | 🔲 待定 |
| **算法组** | `/vel_raw` 速度指令 | 控制组 | 🔲 待定 |
| **算法组** | 任务状态 | 通信组 | 🔲 待定 |

🔲 状态说明：**待各组在《通信协定》第三章填写确认**。

### 4.2 三处"责任缝隙"（必须尽快消除）

以下是链路中**没有明确主人**的地方，是项目风险点：

| # | 缝隙 | 风险 | 建议归属 |
|---|---|---|---|
| 1 | **急停的责任** | 横跨通信（下发）、算法（执行）、控制（实现），三组都以为别人管 | **控制组主导**，通信组负责链路、算法组负责状态机响应 |
| 2 | **指令优先级仲裁** | 同时收到遥控器/LoRa/自主指令时听谁的 | **控制组**（涉及 STM32 固件能力，需实机确认） |
| 3 | **串口资源分配** | 底盘、LoRa、GNSS、雷达都要占 `/dev/ttyUSB*`，插拔顺序一变就冲突 | **通信组统筹**（统一 udev 命名，见《通信协定》2.5 节） |

> 第 3 条是**本项目最紧迫的通信组任务**：`/dev/ttyUSB0` 是按插入顺序分配的，**插拔一次就可能变**。如果各组代码里写死 `ttyUSB0`，某天底盘就会"莫名其妙"连到 GNSS 上去。必须由通信组统一命名（`/dev/rosmaster`、`/dev/lora`、`/dev/gnss`）。

### 4.3 需要通信组主动对接的清单

通信组的核心工作方式是**主动对齐**，不是被动等待。按优先级：

| 优先级 | 对象 | 要定的事 |
|---|---|---|
| ★★★ | 传感组（孙靖凯） | **所有串口设备清单 + VID/PID**（udev 统一命名的输入，**卡住别人的活**） |
| ★★★ | 控制组（廖宇星） | `base_node` 归属与分工；速度话题名/类型/频率；`/odom_raw` 的单位与坐标系 |
| ★★★ | 控制组（崔阳） | 故障判别方法（他要判断异常属电机/控制/通信/里程计哪一类） |
| ★★ | 算法组（罗潇） | 任务状态列表（供遥测上报）；「通信中断」异常的响应策略 |
| ★★ | 算法组（杨博显） | 「前进 150 米」→ 目标点坐标 的转换归属 |
| ★★ | 定位组（张沛文/韦俊杰） | 融合定位话题名/类型/frame_id；150m 场景的**定位精度要求**（决定是否需 RTK） |
| ★ | 视觉组（刘佩琪/黄东旭） | 识别结果是否回传、格式（**建议只传结论不传图像**，LoRa 带宽不足以传图） |

## 五、链路故障定位法

### 5.1 核心方法：找第一个断点

不要瞎试。**从车端往监控端、或从监控端往车端，逐段验证，找到第一个"断掉"的地方**，那就是问题所在。

### 5.2 下行定位表（"发了指令车不动"）

| 检查点 | 命令 | 通过的判据 | 不通过 → 找谁 |
|---|---|---|---|
| ① 指令发出来了吗 | 监控端发送日志 | 有发送记录 | 通信组 |
| ② 车端 LoRa 收到了吗 | `sudo cat /dev/lora \| xxd` | 有十六进制字节 | 通信组（硬件/频段/参数） |
| ③ bridge 解出话题了吗 | `ros2 topic echo /mission_cmd` | 有消息 | 通信组（bridge 节点） |
| ④ 转成速度指令了吗 | `ros2 topic echo /vel_raw` | 有 Twist | 算法组 / 控制组 |
| ⑤ base_node 收到了吗 | `ros2 topic info /vel_raw` | `Subscription count >= 1` | 控制组 |
| ⑥ 串口发出去了吗 | `sudo cat /dev/rosmaster \| xxd` | 有字节（**先关 base_node**） | 控制组 |
| ⑦ 轮子转了吗 | 目视 | 转（**轮子必须悬空**） | 控制组（STM32 固件/PID） |

### 5.3 上行定位表（"监控端看不到数据"）

| 检查点 | 命令 | 通过的判据 | 不通过 → 找谁 |
|---|---|---|---|
| ① 里程计有数据吗 | `ros2 topic hz /odom_raw` | 稳定频率 | 控制组 |
| ② 定位组在发吗 | `ros2 topic hz /odom` | 稳定频率 | 定位组 |
| ③ 遥测节点组装了吗 | `ros2 topic echo /telemetry`（示意） | 有打包数据 | 通信组 |
| ④ 串口发出去了吗 | `sudo cat /dev/lora \| xxd` | 有字节 | 通信组 |
| ⑤ 监控端收到了吗 | 监控端界面 | 有数据显示 | 通信组 / 监控端软件 |

### 5.4 自动化自检脚本（待实机验证）

供实车测试前跑一遍，确认车内链路健康：

```bash
#!/bin/bash
# 车内通信链路自检 —— 通信组
source /opt/ros/humble/setup.bash

echo "=== 1. 环境 ==="
echo "DISTRO=$ROS_DISTRO  DOMAIN=$ROS_DOMAIN_ID"     # 期望 humble / 99

echo "=== 2. 硬件存在 ==="
ls -l /dev/rosmaster /dev/lora 2>&1
groups | grep -q dialout && echo "dialout: OK" || echo "dialout: 缺少权限!"

echo "=== 3. 节点 ==="
ros2 node list | grep -q base_node && echo "base_node: OK" || echo "base_node: 未启动!"

echo "=== 4. 话题两端 ==="
ros2 topic info /vel_raw
ros2 topic info /odom_raw

echo "=== 5. 数据流（轮子请悬空）==="
timeout 5 ros2 topic hz /odom_raw

echo "=== 6. 端到端（轮子请悬空）==="
ros2 topic pub --once /vel_raw geometry_msgs/msg/Twist "{linear: {x: 0.1}}"
ros2 topic echo /odom_raw --once
```

> ⚠️ **安全要求**：第 5、6 步**必须先把车轮架空离地**。绝不在地面直接下发非零速度。

## 附：术语速查

| 术语 | 含义 |
|---|---|
| **UART / 串口** | 通用异步收发器，两个设备间最基础的通信方式（**字节流，无消息边界**） |
| **STM32 扩展板** | 本项目的下位机，直接驱动电机、读编码器、接 SBUS |
| **base_node** | Yahboom 官方 ROS2 节点，负责 ROS 话题 ↔ 串口字节流 的转换（底盘部分） |
| **bridge 节点** | **本项目自写**，负责 ROS 话题 ↔ LoRa 串口字节流 的转换（遥测部分），角色与 base_node 对称 |
| **rosmaster_lib** | Yahboom 官方 Python 库，已封装 STM32 串口协议 |
| **SBUS** | 航模遥控器标准协议，`100000` 波特率、反向电平 |
| **LoRa** | 远距离低功耗无线技术，**CSS 扩频调制**，本项目用 433/470MHz |
| **透传** | 模块不解析数据内容，串口进什么就发什么（**所以车端必须自己写翻译节点**） |
| **半双工** | 同一时刻只能收或发，不能同时（LoRa 的特性，协议里必须处理时分） |
| **DDS** | ROS2 的底层通信中间件，负责话题的自动发现与传输 |
| **DOMAIN_ID** | DDS 的域编号，**不同域的节点互相完全看不见** |
| **QoS** | 服务质量配置（可靠性、持久性等），**两端不匹配就收不到数据** |
| **udev** | Linux 设备管理机制，用于给串口分配**固定的、不随插拔变化的名字** |
| **航迹推算** | 靠里程计累计推算位置，短时准、长时会累积误差（故需 GNSS 修正） |
