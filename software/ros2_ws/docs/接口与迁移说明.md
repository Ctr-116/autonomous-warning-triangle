# 接口与迁移说明

本说明对应当前主线完整迁移开发工作空间（ROS 2 Humble / Ubuntu 22.04 LTS，目标平台 ROSMASTER X3plus）。内容基于实际工程源码与验证架构重写，替代早期单底盘阶段的临时约定与过时描述。

---

## 1. 架构总览与底层通信唯一所有权

### 1.1 单一 BaseNode 独占物理串口
在 ROS 2 原生架构中，底层通信（串口设备 `/dev/rosmaster`，波特率 115200）由 `x3plus_base` 包中的 `base_node`（`BaseNode`）**唯一独占**。
- 严禁任何高层业务节点、动作节点或语音节点直接打开或写入底层串口。
- `BaseNode` 内部采用独立的发送和接收工作线程。写线程维护最新命令单槽，彻底避免控制帧堆积；读线程按严苛的帧头（`FF FB`）、报告长度与校验和协议进行解析与重同步。
- 无论是底盘速度、机械臂舵机角度、灯效控制、蜂鸣器开关，还是版本查询、实测角度读取，全部统一收敛至 `BaseNode`，由其维护物理时序与安全监控。

### 1.2 速度指令、反馈与里程计三者分离
针对历史 ROS 1 命名混乱及控制反馈倒挂的问题，当前主线严格分离三类数据通路：
1. **控制指令入口 (`vel_raw`)**：
   - 类型：`geometry_msgs/msg/Twist`（QoS depth=1，RELIABLE）。
   - 唯一合法的底盘运动速度下发入口。仅接收平面的 `linear.x`、`linear.y` 及 `angular.z`，其余轴必须为零或浮点极小值，否则触发指令非法停机。
2. **底盘真实反馈 (`chassis/velocity_raw`)**：
   - 类型：`geometry_msgs/msg/Twist`。
   - 仅在底层串口解析出最新有效的真实运动报告后触发发布，如实反映轮组实际线速度与角速度。
3. **原始平面里程计 (`odom_raw`)**：
   - 类型：`nav_msgs/msg/Odometry`。
   - 由 `PlanarOdometry` 模块基于底层反馈速度积分生成，支持全向麦克纳姆轮底盘的 $v_x, v_y, \omega_z$。
   - 具备首帧基准对齐、重复帧去重和超时缺口保护功能；底层反馈超时时不跨越断点盲目积分。

### 1.3 导航中继、可选多路复用与单一速度仲裁
为了确保对物理底盘有且仅有一个速度发布源，系统设计了严格的发布者防冲突机制：
- `BaseNode` 持续监控 `vel_raw` 的发布者数量（`count_publishers`）。一旦检测到发布者数量大于 1，立即判定为 `MULTIPLE_COMMAND_PUBLISHERS` 故障，锁定停机并拒绝任何动作。
- **Nav2 速度中继（Relay）**：Nav2 控制器计算的 `cmd_vel` 经专用中继输出至 `vel_raw`。可选的 `velocity_mux` 节点负责控制来源仲裁；本项目未把它当成上游 `twist_mux` 的同名实现。
- **业务模式与重映射隔离**：
  - 基础巡线、追色等单一控制节点在启动时将自身的 `cmd_vel` 重映射至 `vel_raw`。
  - 搬运（`transport`）、取物（`takethings`）、多点巡航（`waypoints`）模式通过 Nav2 发送目标或取消请求，由导航中继负责最后的速度输出和停车，避免业务节点另建 `vel_raw` 发布者。

## 2. 坐标系、TF 与多机命名空间

### 2.1 命名空间与相对话题设计
- `BaseNode` 及各功能包节点内的话题名称均采用相对命名（如 `vel_raw`、`chassis/velocity_raw`、`odom_raw`、`imu/data_raw` 等）。
- 当节点推入命名空间（如 `<robot_namespace>`）运行时，所有通信话题、参数、服务以及 `tf`、`tf_static` 均通过 `GroupAction` 与 `PushRosNamespace` 自动作用域化，满足多机协作与系统隔离需求。

### 2.2 坐标系定义与 TF 树维护
- 默认关键坐标系（Frame ID）：
  - 里程计父系：`odom`
  - 机器人基座：`base_footprint`（连接 `base_link`）
  - 惯性测量单元：`imu_link`
- 参数 `publish_odom_tf` 决定是否由 `BaseNode` 广播 `odom -> base_footprint` 变换：
  - 在纯单底盘或基础调试下，由底盘节点直接广播该 TF。
  - 启用 EKF 并由它发布 `odom -> base_footprint` 时，关闭底盘对同一条 TF 的发布。AMCL/SLAM 通常提供的是 `map -> odom`，仍需底盘或 EKF 提供 `odom -> base_footprint`；不能仅因开启 AMCL/SLAM 就把这条里程计 TF 删除。
- 所有 Frame ID 严格要求非空且不带前导斜杠 `/`，完全符合 ROS 2 TF2 命名规范。

## 3. 机械臂与外设接口

### 3.1 机械臂使能安全门禁 (`enable_arm`)
- 为防止启动时因未预期信号或机械干涉导致机械臂意外失控，`BaseNode` 设置了 `enable_arm` 参数门禁（动态布尔参数，默认 `false`）。
- **门禁放行条件**：
  $$\text{Gate Open} \iff (\text{enable\_arm} == \text{true}) \land (\neg \text{guard.fault}) \land (\neg \text{transport.error}) \land \text{fresh\_motion}$$
- 当门禁处于关闭状态、系统发生故障锁定或底层反馈超时时，任何写入目标舵机角度的请求都会被直接忽略并清空；在发生急停或重置为未使能时，系统主动调用 `clear_accessories()` 截断下发，杜绝指令滞后堆积。

### 3.2 实际消息定义与服务契约

#### 舵机控制指令：`ArmJoint.msg`
机械臂目标角度下发话题为 `TargetAngle`，类型使用工程实际消息 `yahboomcar_msgs/msg/ArmJoint`：
```text
int32 id          # 单舵机 ID（1..6）
int32 run_time    # 运动时间（毫秒，0..2000）
float32 angle     # 单舵机目标角度
float32[] joints  # 6 轴联合数组（非空时必须严格包含 6 个舵机目标角度）
```
- 控制方式一（多轴联动）：若 `joints` 数组非空，则必须传入长度为 6 的合法角度序列，分别对应 1 到 6 号舵机。
- 控制方式二（单轴控制）：若 `joints` 为空，则解析 `id`（1..6）与对应 `angle`。
- 角度范围经过严格限幅校验：1..4 号舵机为 $[0^\circ, 180^\circ]$，5 号舵机为 $[0^\circ, 270^\circ]$，6 号夹爪为 $[30^\circ, 180^\circ]$。

#### 真实实测角度服务：`RobotArmArray.srv`
实测角度查询服务为 `CurrentAngle`，类型使用工程实际服务 `yahboomcar_msgs/srv/RobotArmArray`：
```text
# Request
string apply
---
# Response
float64[] angles
```
- 在硬件模式 `use_mock:=false` 下，服务仅返回真实串口上报的最新有效实测角度；模拟模式返回明确的模拟反馈，不作为实体测量证据。
- 若反馈超时（`arm_time` 超出容差）或尚未收到硬件测量，服务端响应一律返回**空数组 `[]`**。系统严禁用模拟目标值或伪造数据充当真实反馈。
- 同时，`BaseNode` 在收到新鲜实测角度时，通过相对话题 `ArmAngleUpdate` 发布 `ArmJoint` 消息（`msg.joints` 填充 6 轴实测值），供外部状态监控。

### 3.3 灯效与蜂鸣器协议区别
底盘外设接口明确区分了特效灯光与静态 RGB，避免协议混淆：
- **`RGBLight`**（话题类型 `std_msgs/msg/Int32`）：特效控制入口。仅接受整型效果编号 **`0..6`**（如呼吸灯、流水灯、彩虹等预设动画固件特效），超出范围的数值将被警告并丢弃。
- **`RGBColor`**（话题类型 `std_msgs/msg/UInt32`）：静态 24 位色彩输入。接收十六进制色彩数值 `0xRRGGBB`（数值范围 `0x000000..0xFFFFFF`），底层拆解为高 8 位 Red、中 8 位 Green、低 8 位 Blue 并写入所有板载灯珠。
- **`Buzzer`**（话题类型 `std_msgs/msg/Bool`）：蜂鸣器控制，直接传递布尔开关信号。

## 4. 语音交互与业务状态机

### 4.1 九大核心语音模式
语音控制顶层统一由 `yahboomcar_voice_ctrl/launch/voice.launch.py` 进行编排调度。系统支持且仅支持以下 9 种标准模式名称（`mode` 参数）：
1. `base`：底盘基础运动控制（前进、后退、自旋、定速巡航）。
2. `arm`：机械臂动作组触发与特定姿态执行。
3. `study`：机械臂示教录制、动作存储与轨迹回放。
4. `line`：视觉巡线与车道保持。
5. `color_tracker`：单色识别与云台/底盘闭环跟随。
6. `color_identify`：特定目标颜色检测与视觉确认。
7. `transport`：色块分拣、搬运与导航复合任务状态机。
8. `takethings`：特定物品抓取与交互作业。
9. `waypoints`：预设导航点巡航（原始 5 个固定点导航与到达播报）。

### 4.2 语音串口安全默认与异步 Action 机制
- **串口隔离安全**：启动参数中 `enable_serial` **默认设为 `false`**。在无实体语音识别硬件接入或本地测试验证时，不会占用或盲目打开宿主串口设备；配合 `use_mock:=true` 可进行全链路逻辑仿真。
- **Action 异步目标与取消机制**：
  - 导航业务通过 ROS 2 Nav2 Action 异步调用；机械臂业务使用计时状态机、目标话题和实测角度服务，MoveIt 轨迹执行另使用控制器 Action。
  - 控制端使用非阻塞的异步目标发送（`send_goal_async`）和异步取消（`cancel_goal_async`），并严密监控执行反馈。
  - 当收到急停指令、切换模式或发生导航异常时，安全状态机能够瞬间向执行端发出 Cancel 请求，杜绝在同步阻塞调用中因超时或死锁引发失控。

### 4.3 业务测试与 Nav2 本体验证的分离
在开发与持续集成测试中，系统对两类测试进行了严格解耦：
- **业务状态机测试（Mock Nav2）**：验证搬运、取物及多点巡航状态机的决策分支、超时处理与重试逻辑。该套件连接明确标注的模拟 Nav2 动作服务器，验证状态机在收到 ACCEPTED、SUCCEEDED、CANCELED 等各类状态下的行为流转。
- **Nav2 实际软件闭环测试**：运行实际 Nav2 的代价地图、规划、控制、行为、BT 和可选 AMCL 节点，接入合成地图、雷达与模拟底盘，验证目标到达和取消后停车。测试不代表实体小车避障或 slam_toolbox 建图质量验收。
- 二者界限明确，严禁将“业务状态机模拟测试通过”与“Nav2 系统实际闭环通过”混为一谈。

## 5. 机械臂控制：MoveIt 2 与底盘 SDK 真实驱动的边界

当前系统在机械臂控制上明确界定了算法层与硬件驱动层的实现边界：
- **MoveIt 2 规划层**：
  - 基于 OMPL 规划管道与 `ros2_control` 接口，完整支持轨迹生成、碰撞检测、笛卡尔路径规划与夹爪动作。
  - **当前控制器状态**：MoveIt 控制器当前运行于 **`ros2_control` 模拟硬件接口（Mock Hardware Interface）**，用于规划算法、运动学逆解及关节状态总线的验证。
- **底盘 SDK 真实伺服通路**：
  - 底盘主板硬件上的真实总线舵机协议由 `BaseNode` 经由真实串口协议处理。
  - 已在 Linux 虚拟串口（PTY）环境中验证实际 SDK 的舵机目标编码、只读轮询及角度解算；尚未进行实体电路板通信验收。
  - 实体机械臂与 MoveIt 2 `ros2_control` 硬件驱动读写循环（`read()` / `write()` 桥接至串口舵机总线）的全面实机验收属于后续实车阶段目标。

## 6. 视觉与 AI 推理环境与硬件边界

针对视觉检测算法，本工作空间在标准 x86_64 Ubuntu 22.04 LTS 环境下完成了纯推理功能与 ROS 消息链路的打通，但明确划分了软件推理与边缘硬件的验证边界：

| 算法框架 / 模块 | 离线与推理验证状态 | 依赖与环境特征 | 边缘硬件未验证项 |
| :--- | :--- | :--- | :--- |
| **SSD & OpenPose** | 原生图像、IR、点云流输入下，真实模型前向推理与 DDS 消息链路已调通。 | 系统级 OpenCV / C++ 依赖链路。 | Jetson CSI 相机驱动、实际帧率稳定性。 |
| **YOLOv11** | 采用原 ONNX 权重，通过 ONNX Runtime CPU 完成真实正样本推理检测。 | 私有环境配置，不依赖冗余的 torch/ultralytics。 | Jetson TensorRT 加速器、ARM64 引擎部署。 |
| **MediaPipe 0.10.9** | 验证手势（21 点）、人体骨骼（33 点）正样本检测与 Objectron 点云处理。 | 严格匹配系统 OpenCV ABI 的旧版专用 Python wheel 环境。 | ARM64 交叉编译包兼容性、实际计算负载。 |
| **dlib & Haar** | 使用原始 99.7 MB 权重完成 68 点人脸特征点定位与图像流回环。 | 本地源码构建的 `dlib==19.24.6`，私有目录加载。 | ARM64 边缘端 CPU 算力与内存开销。 |

> **边界声明**：上述 AI 推理的通过证明了模型权重、推理接口及 ROS 图像序列化管道的正确性；并不代表相同 Python wheel 或二进制库可无缝直接拷贝至 Jetson Linux (ARM64) 运行，亦未在真实物理传感器（如 Astra 深度相机、USB 广角相机）上进行过全帧率实机验收。

## 7. ROS 1 到 ROS 2 原生架构映射体系

本项目并非机械地逐行转换代码，而是遵循 ROS 2 原生设计规范重构整体架构：

| 体系维度 | 原始 ROS 1 (Noetic / Melodic) | 原生 ROS 2 (Humble) 架构实现 |
| :--- | :--- | :--- |
| **构建系统** | `catkin_make` / `catkin`，`CMakeLists.txt`（宏命令繁杂）。 | `ament_cmake`（C++ 包）与 `ament_python`（Python 包），现代标准 CMake 与 `setup.py` / `setup.cfg` 组织。 |
| **核心客户端** | `rospy`（依赖隐式全局初始化、全局时间戳）。 | `rclpy` 继承自 `rclpy.node.Node`，显式节点上下文、时钟（`ClockType.STEADY_TIME`）与生命周期管理。 |
| **节点编排** | XML `.launch` 格式，标签静态配置。 | Python `.launch.py`，支持 `GroupAction`、`OpaqueFunction`、动态条件判断与程序化参数校验。 |
| **参数管理** | `rosparam` 全局参数服务器，动态调整依赖 `dynamic_reconfigure`。 | 节点私有声明参数（`declare_parameter`），内置只读约束与动态回调 `add_on_set_parameters_callback`。 |
| **通信机制** | TCPROS / UDPROS，强依赖 Master 节点（`roscore`）。 | 基于 DDS 标准的分布式通信，去中心化发现，原生支持细粒度 QoS 配置（可靠性、历史深度、传感器数据配置）。 |
| **长时任务** | `actionlib`（复杂的多话题封装状态机）。 | 原生 ROS 2 Action 抽象，规范的 Client/Server 异步 Goal 处理与 Cancel 回调接口。 |

## 8. 遗留系统边界与非范围声明

在本次工作空间迁移梳理中，部分原厂或历史项目遗留算法已明确界定为**用户指定范围外**或**由 ROS 2 上游标准方案直接替代**，不再进行逐行死守式移植：
1. **已由标准上游方案替代的模块**：
   - 原始 Cartographer ROS 1 定制封装、Hector SLAM、Gmapping 等已由 ROS 2 官方推荐的 `slam_toolbox` 与 `Nav2` 统一标准流水线替代。
2. **当前工作范围外或未连接实车保留项**：
   - 历史仓库中涉及的 Gazebo 复杂动态仿真环境、Warehouse 仓储仿真场景；
   - 针对老旧相机的特定标定实验与尚未部署的第三方 ORB-SLAM SDK；
   - 实车 IMU 物理安装角动态校准、真实电池放电曲线建模与硬件级物理急停回路。

## 9. 快速上手：主线标准操作流程

### 9.1 环境配置与工程构建
```bash
# 1. 检查并安装构建依赖（基于 Ubuntu 22.04 LTS 与 ROS 2 Humble）
bash scripts/install_dependencies.sh --check-only

# 2. 编译整个工作空间（支持多线程并发编译）
bash scripts/build.sh

# 3. 加载环境变量
source scripts/environment.sh

# 4. 执行自动化单元与集成检查
bash scripts/test.sh
```

### 9.2 启动模拟验证底盘与系统接入
在无物理小车连接时，可通过虚拟底盘模式快速启动系统基础节点：
```bash
# 启动底盘节点（模拟模式，机械臂门禁关闭，提供 vel_raw 与安全监控）
ros2 run x3plus_base base_node --ros-args -p use_mock:=true -p enable_arm:=false
```

### 9.3 启动语音控制与业务模式
以最基础的模拟底盘运动语音模式为例：
```bash
# 启动语音底盘控制模式（开启虚拟底盘，默认关闭物理语音串口）
ros2 launch yahboomcar_voice_ctrl voice.launch.py \
  mode:=base \
  start_base:=true \
  use_mock:=true \
  enable_serial:=false
```
如需进入包含机械臂的业务模式（如搬运 `transport`），请显式核实 `enable_arm:=true`，并确保各上游导航及视觉节点就绪后通过服务打开使能开关。
